Run the plan's day-end sections from `docs/plans/NEXT_BUILD_PLAN.md` ("FINAL DAY-END BUILD VERIFICATION & PULL REQUESTS") in this order: A, B, D, E, the one push, the Jira Done transitions after the merge, C, then the deferred gates (MOM-75, docs/mom-75-plan-execution-spec.md section 2.3). Stop on the first failure and show it. Stop only at the plan's approval gates, at the one push, and at the Done transitions.

Rules for every step:
- Before each step, say in one line what you are about to do and why.
- Run git commands one at a time (never chained with `&&`) and stop on the first error.
- CLAUDE.md wins: `main` is protected. Never merge into `main` locally, never push `main`, never push a branch without my explicit OK.
- Stage files by name. Never stage `docs/FAILURE_LOG.md`, `docs/RAID_LOG.md`, `AGENTS.md`, `supabase/.branches/` or `supabase/snippets/` except the log entries I approve in step D, and then only those entries.

0. **The day's branches.** `git fetch origin`, then `git branch --no-merged origin/main`; for each branch show `git log origin/main..<branch> --oneline`. This list, plus the branches steps D and E create, is "the day's branches". If it is empty and there is nothing to sync, say so and stop.
1. **A. Build checks.** Follow section A of the plan: on each day's branch in turn (`git switch <branch>`), run `npx tsc --noEmit`, `npm test`, `npm run build` and `npm run plan`. A docs-only branch needs only `npm test` and `npm run plan`.
2. **B. Production verification, only if a migration was applied today** (`git log --all --since=midnight --name-only -- supabase/migrations` shows it). On this Windows machine the loop runs in Git Bash, which is the shell Claude Code already uses. Run section B of the plan: `npx supabase migration list` (local and remote must match), then every file in `supabase/verify/` against production; every script must report `false 0` and a non-zero `true`. Then the user count: it must be exactly 1 (the standing smoke-test account). Report the totals.
3. **D. Backlog and Jira sync.** Follow the fenced prompt in section D of the plan, on its own branch, as written. D runs before anything has merged, so it never moves a ticket to Done. It may only comment on tickets, create tickets for un-ticketed items, and propose "Closed" for obsolete or redundant ones: list each proposed Closed with its reason and wait for my OK before making it. It ends with the RAID and failure log review (MOM-92): list the day's `unreviewed` entries in numbered form, ask "predicted it? yes / no / partly" for each failure, wait for my plain-language reply, remove the `unreviewed` marks only on approved entries, and commit only those (stage only the approved entries; the rest stay uncommitted in the working copy). I never edit a file or run a command for this.
4. **E. Tomorrow's plan.** Follow the fenced prompt in section E of the plan: archive the finished plan to `docs/plans/archive/YYYY-MM-DD.md` before writing the new one, write the new plan, run `npm run plan:check -- --strict` until it reports no errors and no warnings, and commit both on a docs branch. Do not merge it.
5. **The one push.** Show `git log origin/main..<branch> --oneline` for every day's branch, including the step D and E branches, and wait for my explicit OK. On OK, run `git push -u origin <branch>` once per branch (never `main`). Print the pull request link for each (`https://github.com/<owner>/<repo>/pull/new/<branch>`, from `git remote get-url origin`); run `gh pr create` only if `gh` is installed and I say yes. Then tell me: both CI jobs, `checks` and `database`, must be green on each pull request; a branch with a migration needs its production `db push` and the verify scripts after CI is green and my OK and before it merges; each pull request merges with a merge commit. Wait for me to say they are merged.
6. **Tidy.** After the merge: `git switch main`, then `git pull --ff-only`, then `git branch -d` for each merged day's branch (never `-D`).
7. **Jira: Done transitions, only for what has merged.** For each ticket whose pull request merged today (the merge commits on `origin/main` since midnight, and the `(MOM-n):` commit prefixes), list the proposed transition to "Done" with the ticket's acceptance criteria, each marked met or unmet with its evidence (a test, a commit, a production check, a gate item). A ticket with an unmet criterion or a live gate still pending stays open, with a comment saying what remains. List any epic whose children are now all Done or Closed, with those children. Wait for my OK, then make exactly the transitions I approved and comment what shipped. Never move a ticket to Done before its pull request has merged.
8. **C. Live checks, after Vercel has deployed.** Run `npx vercel ls --prod` and read the newest production deployment's status; explain it in one line ("Ready: serving the merge", "Building: wait", or "Error: open the build log"). If the Vercel CLI cannot be used, ask me to read it from the dashboard. Then `curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" https://momentum-app-eight-chi.vercel.app/` (expect 307 to `/login`) and the same for `/login` (expect 200).
9. **Deferred gates.** Print `docs/plans/.pending-live-checks.md` and walk each item with me. When I confirm they are done, empty the file. Remind me: sign in as the standing smoke-test account for the live checks (you never see its password), and the day-end is finished only when I say so.
